# 重置次数逐条操作与预约记录管理设计

## 背景

当前“重置次数明细”弹窗把“立即重置”和“预约重置”放在底部公共操作区。当账号存在多条重置次数记录时，操作入口与单条记录相距较远。独立“重置记录”页面已经显示活动预约和历史日志，但活动预约不能修改时间，取消预约没有二次确认，日志也不能删除或清空。

Codex 重置消费接口只接受账号 ID，不接受重置次数 ID。因此，单条记录后的按钮是账号级操作入口，不能承诺消费按钮所在行对应的重置次数。

## 目标

- 在每条重置次数记录后显示该账号的“立即重置”和“预约重置”操作入口。
- 明确说明实际消耗的重置次数由服务端决定，避免把账号级操作误解为指定记录消费。
- 支持修改尚未到期、尚未开始执行的预约时间。
- 取消预约前显示二次确认。
- 支持删除单条重置日志和清空全部重置日志，两个操作都需要二次确认。
- 保持“预约仅在应用运行期间执行”和“每个账号最多一个活动预约”的现有约束。

## 方案选择

采用“逐条展示账号级操作入口”方案：每条记录右侧都显示操作按钮，但不把重置次数 ID 写入新预约或新日志。弹窗内显示固定说明“按账号执行，实际消耗记录由服务端决定”。

不采用以下方案：

- 保留底部公共操作按钮：实现简单，但不能满足多条记录逐条放置入口的布局要求。
- 把点击行的重置次数 ID 保存为预约目标：当前服务端无法按 ID 消费，这会制造无法兑现的指定消费语义。

## 重置次数弹窗

### 记录布局

每条重置次数记录保留状态、序号、发放时间和可用截止时间，并在记录末尾增加操作区：

- “立即重置”：触发现有账号级立即重置流程。
- “预约重置”：打开独立预约时间弹窗。
- 记录不可用、已使用或已过期时，两个按钮保持显示但禁用。
- 任一账号级重置操作进行中时，同一弹窗内所有记录的操作按钮禁用，防止重复提交。

弹窗底部只保留“关闭”操作，不再重复显示立即重置和预约入口。

### 已有预约

账号已有 `scheduled` 或 `running` 预约时：

- 所有可用记录后的“立即重置”按钮禁用，避免预约与立即消费冲突。
- “预约重置”按钮改为“已预约”，并显示预约标识。
- 点击“已预约”关闭弹窗并进入“重置记录”页面。
- 不在重置次数弹窗展示预约时间、倒计时、修改或取消操作。

### 账号级语义

每条记录后的按钮仅用于把操作放到用户当前查看的位置。点击任意可用记录后的按钮时，前端仍只向现有消费或预约流程传递账号，不传递 `resetCreditId`。界面说明必须在记录列表附近持续可见，不能只依赖悬浮提示。

## 预约时间创建与修改

### 共用时间弹窗

现有 `ResetScheduleModal.vue` 同时支持创建和修改：

- 创建模式：标题和确认按钮使用“设置预约重置时间”“保存预约”。
- 修改模式：接收现有预约 ID 和时间，打开时预填本地日期时间；标题和确认按钮使用“修改预约时间”“保存修改”。
- 两种模式都拒绝空值、无法解析的值和不晚于当前时间的值。
- 保存期间禁止关闭弹窗和重复提交；失败时保留用户输入，成功后关闭。

### 修改约束

修改时间通过新的 Rust 原子状态命令完成。后端在同一个锁内读取、校验并写回状态：

- 预约 ID 必须存在。
- 当前状态必须为 `scheduled`。
- 当前预约时间必须仍晚于命令执行时刻，已经到期或已被调度器领取的预约不能修改。
- 新预约时间必须晚于命令执行时刻。
- 修改只更新 `scheduledAt`，保留预约 ID、账号、创建时间和其他字段。

如果修改与调度领取同时发生，Rust 状态锁决定唯一结果：修改先成功则调度器按新时间执行；领取先成功则修改返回“预约已开始执行或无法修改”。

## 重置记录页面

### 活动预约

每条 `scheduled` 预约显示账号、预约时间、实时倒计时、修改按钮和取消按钮。`running` 预约继续显示“执行中”，不显示可操作的修改或取消入口。

- 点击修改按钮打开共用时间弹窗并预填当前时间。
- 点击取消按钮先显示“确认取消该预约？”二次确认。
- 用户确认后才调用现有取消命令；取消成功后预约从活动列表移除，并继续产生一条“已取消”日志。
- 修改或取消进行中时，对应按钮显示加载状态并禁止重复操作。

### 重置日志

日志区标题栏增加“清空日志”按钮，每条日志末尾增加删除按钮：

- 单条删除前显示“确认删除该条重置日志？”二次确认。
- 清空前显示“确认清空全部重置日志？此操作不可恢复。”二次确认。
- 没有日志时禁用清空按钮。
- 日志删除只影响日志集合，不修改活动预约。
- 删除和清空通过 Rust 原子状态命令执行，保证与预约执行追加日志并发时不会用旧快照覆盖新状态。
- 单条日志 ID 不存在时返回错误，不把无效删除显示为成功。

## 接口与状态边界

新增以下 Tauri 命令和前端服务函数：

- `update_codex_scheduled_reset(schedule_id, scheduled_at)`：原子修改预约时间并返回最新 `ResetState`。
- `delete_codex_reset_log(log_id)`：原子删除单条日志并返回最新 `ResetState`。
- `clear_codex_reset_logs()`：原子清空日志并返回最新 `ResetState`。

`App.vue` 继续作为协调层：

- 管理创建/修改共用时间弹窗的模式和目标预约。
- 所有状态修改继续经过现有串行前端队列 `runResetStateMutation`。
- 分别维护修改预约、取消预约、删除日志和清空日志的忙碌状态。
- 操作成功时采用命令返回的完整最新状态；失败时保留当前状态并显示后端错误。

现有 `resetCreditId` 可选字段只用于兼容读取旧的本地状态文件。新建预约、立即重置日志、预约执行日志和取消日志都不新增该字段，也不根据该字段决定消费对象。

## 数据与兼容性

- 不改变 `reset-state.json` 文件位置和顶层结构。
- 不增加必须迁移的持久化字段，旧文件可以继续读取。
- 日志仍按发生时间排序并最多保留 200 条。
- 清空日志后，后续预约执行产生的新日志正常写入。
- 不删除终态预约的现有持久化清理规则。

## 错误处理

- 前端基础校验用于即时提示，Rust 后端重复执行关键校验，不能依赖前端保证状态正确。
- 修改、取消、单条删除和清空失败时不显示成功消息。
- 状态竞争导致操作对象已变化时，使用后端返回的明确错误提示用户刷新。
- 前端防重复状态只改善交互；Rust 原子命令负责最终一致性。

## 验收标准

1. 多条重置次数记录各自在末尾显示“立即重置”和“预约重置”按钮，底部不再重复显示这两个按钮。
2. 可用记录的按钮可操作，不可用记录的按钮禁用；界面明确提示操作按账号执行且实际消费记录由服务端决定。
3. 账号已有活动预约时，每条可用记录显示“已预约”入口，立即重置不可用；点击后进入“重置记录”页面。
4. `scheduled` 预约可打开预填当前时间的修改弹窗并保存未来时间，列表时间和倒计时立即更新。
5. 已到期、`running` 或不存在的预约不能修改。
6. 取消预约必须经过二次确认，重复点击不会发出重复取消请求。
7. 每条日志可在二次确认后单独删除；日志区可在二次确认后清空全部日志。
8. 删除日志不影响活动预约；清空与调度追加日志并发时不产生旧状态覆盖。
9. 预约调度仍只在应用运行期间执行，每个账号仍最多存在一个活动预约。
10. 前端测试、类型检查和生产构建通过；Rust 状态存储测试、格式检查和完整测试通过。

## 非目标

- 不支持指定某个重置次数 ID 进行消费。
- 不增加应用关闭后的后台调度、系统任务或补偿执行。
- 不改变账号额度接口、重置消费接口、应用图标或打包配置。
- 不提交、推送或发布本次工作区改动。
